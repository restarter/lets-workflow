# Protocol: agents - dispatch, reports, members

Loaded by: `/lets:ask`, `/lets:backlog`, `/lets:check`, `/lets:execute`, `/lets:opinion`, `/lets:plan`, `/lets:research`, `/lets:review`, `/lets:team` - Read before the first dispatch step. Core rules keep the always-on part: never `general-purpose` or another non-`lets:*` subagent type for expert work; the who-does-what line (directed search vs exploration is the FACT route of `protocol/roles.md`).

| rule | detail |
|---|---|
| expert dispatch | launching expert agents for `/lets:review`, `/lets:github-pr`, `/lets:opinion`, `/lets:ask`, `/lets:plan`, `/lets:backlog`, `/lets:research` uses ONLY `lets:*` agents (`lets:architect`, `lets:security`, ...) |
| web data-gatherers (carve-out) | `/lets:research`'s per-sub-question web fetchers are data gatherers on the default web-capable subagent, NOT expert dispatch - `lets:*` agents have no web tools (no WebSearch / WebFetch). The `lets:*`-only rule covers research's `lets:skeptic` cross-check, not its web fetch |
| `lets:actor` | a meta-agent: needs an explicit user request + a personality source (URL or file path); never auto-selected; fetch the personality with the `actor-fetch-personality` skill before dispatch |
| reports travel by file | every agent dispatched through the Task / Agent tool gets a `REPORT_FILE` from the `agent-report` skill and writes its report there; the orchestrator reads every report in full and never treats a missing report as "no findings" - it is a loud gap in the output and in the saved artifact. `--workflow` paths are exempt (their agents return through StructuredOutput) |
| members | implementers and standing-team members are spawned, messaged and dismissed only through the `member-run` skill - member-run is the one path; the recorded agent id is the address (`Member:` lines in a team file, `agent_id` in an execute run record) - `ListAgents` only says busy; dismissals are recorded before the dismiss |
| tracker data | resolving tracker verbs is ORCHESTRATOR-ONLY - subagents never call tracker verbs (they do not receive the adapter file). A command that needs tracker data inside a subagent prompt pulls it itself and INJECTS it as fenced data. No exceptions, no carve-outs |

## Team mode

In a team worktree the lead's dispatches go to the team's members first (lets-mpjhc). A command's dispatch step points here; the mechanics are member-run `op=route` / `op=receive`.

1. Before a phase's `op=open` / `op=add`: `Skill(skill: "lets:member-run", args: "op=route command=<command> roles=<the phase's roles> fallback=<one-shot|inline|run>")` - `roles=` are bare role names (`architect`, not `lets:architect`), matched against the roster's `role` column; `--solo` adds `solo`; a later phase of the same run passes `team=<c>` from the first answer. `TEAM off` -> the phase runs exactly as today.
2. Report names: one distinct name per member line, allocated before the `op=open` / `op=add` call - the first member line of a role `{role}`, the next `{role}-2`, `{role}-3`, ..., skipping every name already allocated in this run (a `TAKEN` answer -> the next free suffix) - plus today's names for the fallback items, in the same call. Two members of one role never share a report file.
3. One brief per member line, written to `.lets/cache/route-<REPORT_DIR basename>-<name>.md`: line 1 `REPORT_FILE: <path>`; then the phase prompt's mode line and shared context once; then `## Item <k>: <label>` per item, each holding the body that item's Task prompt would carry; then one line naming the teammates' addresses (each reachable `Member:` of this lead session: name, role, agent id) and the rule that goes with them: "re-read the team file's `## 7` before you send; a name with a `Dismissed:` or `= gone` line is not reachable - route through the lead"; last, "Write ONE report, one `## Item <k>` section per item in item order, last line REPORT-END". Several member lines of one role -> items dealt round-robin.
4. Before ANY send to a member id this run already holds - a later phase, opinion's challenge - re-read `## 7`: a `Dismissed:` or `= gone` line for it now -> its items go to the fallback, announced. Send every member brief - `Skill(skill: "lets:member-run", args: "op=next scope=<c> name=<name> id=<agentId> brief-file=<brief> report-file=<path>")` - BEFORE the phase's fallback Task calls, then make the Task calls as today, in one message. `member_busy` -> `op=add` fresh fallback names for that member's items and dispatch them with the fallback; the `{role}` file opened for it is never collected. `agent_gone` -> the same, and record `Member: <name> = gone (lead <session6>)` in the team file.
5. Collect the fallbacks with `op=collect` as today and each member with `op=receive` (READ EVERY REPORT IN FULL) - before EVERY `op=receive` re-read the team file's `## 7` and pass `dismissed` when the member has a `Dismissed: <name> (lead <session6>)` line now (the owner may dismiss it while the phase waits). A member GAP is the GAP of every item it carried; `GAP ... gone` also records `Member: <name> = gone (lead <session6>)`. The phase ends when every member line is `RECEIVED` or `GAP`; on `WAITING` / `NUDGED` print `waiting for <c>-<name>: <report path>` and end the turn - the next notification, or a resumed session, re-enters with `op=receive` on that path. A phase with no fallback Task calls ends the turn right after the sends; `op=receive` runs on the member's notification.
6. Every non-member `ROUTE` line is announced in one line: `{role}: {fallback} - {why}` (`not-in-roster`, `busy`, `not-live`, `spawning`).
7. `--workflow` -> no route; in a team worktree print once `team worktree - --workflow runs its own agents, not the team's`.
